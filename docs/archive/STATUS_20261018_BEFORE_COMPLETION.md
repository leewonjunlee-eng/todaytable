### 먼저 해결할 오류

1. **재매칭 변수 가림:** `lib/lifecycle-service.ts:138` 부근에서 루프 뒤쪽의 `weights`, `minScore` 선언이 같은 블록 앞쪽 참조를 가립니다. 타입 오류 4개와 재매칭 테스트 2개 실패를 재현했습니다. 뒤이어 테이블을 찾지 못하는 테스트도 실패하며 앞선 시나리오 실패의 영향 여부를 함께 확인해야 합니다.
2. **누락 import:** `app/api/admin/matching-rules/route.ts:66`에서 `databaseProvider`가 선언되지 않았습니다. GET은 기본 정책을 읽지만 PUT은 기존 `matching_rules`에 쓰므로 정책 저장 경로도 통일해야 합니다.
3. **주기 워커:** `worker/index.ts:331`이 `scheduled_jobs.updated_at`을 조회하지만 해당 열은 없습니다. `:349`의 `query()` 세 번째 인자도 SQL 문자열 대신 배열입니다. `tick()`이 이 스케줄러를 먼저 호출해 Journey 워커 테스트가 실패합니다.
4. **구형 테스트 DB:** `tests/source-data.test.ts`의 마이그레이션 목록이 013까지만 반영합니다(012도 누락). 변환 코드가 추가한 `users.is_demo` 열을 찾지 못합니다. 전체 마이그레이션 적용과 모의 표시 검증이 필요합니다.

### 테스트 외에 소스에서 확인한 미완성 부분

- `participant_preferences`에는 `feedback_id` 열이 없는데 후기 POST가 해당 열에 씁니다. 선호 확인을 동반한 저장 경로를 수정·검증해야 합니다.
- `lib/feedback-service.ts`는 없는 `journey_feedback.application_id`를 참조합니다. PostgreSQL 전용 정규식·LATERAL·집계를 SQLite와 호환해야 합니다.
- 신호 집계 함수가 자체 BEGIN/COMMIT을 수행하지만 워커도 트랜잭션을 관리합니다. 피드백 수정·삭제 시 오래된 신호 제거, 후기 수와 관심사 수 구분, 모의 데이터 제외를 검증해야 합니다.
- 후기 API의 실제 출석 검증·개인화 철회와 프런트엔드 연동, 운영 인사이트는 완료 기준을 충족하지 못했습니다.

위 항목은 정리 과정에서 발견한 후속 개발 대상입니다. 이번에는 애플리케이션 동작이나 마이그레이션을 변경하지 않았습니다. 기존 수정 파일 3개의 줄 끝 불필요한 공백만 정리했습니다.
