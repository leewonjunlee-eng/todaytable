# 우연한 식탁 제품 확장 계획

작성: 2026-10-17. 최초 제품 확장 계획이다. 이후 일부 로컬 구현을 중단했다가 2026-10-18 전체 작업을 재개했다. 최신 구현·검증·운영 반영 결과는 [현재 현황](STATUS.md), 과거 재개 명세는 [구현 인수인계](IMPLEMENTATION_HANDOFF.md)를 확인한다.

## 1. 제품 목표

참가자가 가능한 일정과 취향을 알려주면 시스템이 만남을 준비하고, 운영자 3명은 공동 문의함과 예외 상황을 관리한다. 문의와 후기에서 얻은 근거를 바탕으로 매칭 품질과 재참여 경험을 개선한다.

| 대표님의 의도 | 이번 확장 | 판단 지표 |
| --- | --- | --- |
| 획득·전환 | 문의 접근성, 이해하기 쉬운 참가 절차, 결제·매칭 상태 안내 | 방문→조건 등록→모의 결제 전환, 문의 후 참가 전환 |
| 매칭 품질 | 매칭 기조, 비교 미리보기, 개인화된 배정 이유 | 확정률, 대화 만족도, 미매칭률, 제외 조건 위반 0건 |
| 반복 참여 | 종료 후 후기, 다음 식탁 추천, 확인 가능한 선호 업데이트 | 후기 응답률, 실제 재신청률, 반복 참가자의 만족도 |
| 운영 효율 | 3인 공동 문의함, 담당·분류·처리 이력, 예외 중심 업무 | 첫 답변 시간, 해결 시간, 미배정·장기 미처리 문의, 수동 개입 횟수 |

모의 데이터 지표와 실제 참가자 지표는 분리한다. 모의 후기·결제·참가를 실제 개선 성과나 학습 근거로 계산하지 않는다.

## 2. 현재 구현과 확장 범위

- 구현됨: 참가 조건·일정 입력, 모의 결제·환불, 자동 매칭·재배치, 식당·방 준비, 채팅, 출석, 후기 저장, 알림, 운영 예외 관리.
- 매칭 규칙: 전역 숫자 가중치 입력과 버전 기록은 있으나 쉬운 기조 선택, 회차별 정책, 결과 비교가 없다.
- 후기: 점수·텍스트·재참여 의향·상대 선호를 저장한다. 다음 매칭에는 주로 DISLIKE 제외와 재회 이력이 반영된다. 긍정적 경험과 불편 요인의 개인화·품질 검증은 부족하다.
- 문의: 참가자 문의 접수, 공동 답변, 카테고리와 처리 이력 기능이 없다.
- 운영자: ADMIN 권한은 있으나 3인 협업·개인별 업무함·담당자 권한 구분이 없다.
- 디자인: 크림·브라운·세이지 무드가 있으나 운영 화면의 정보 밀도, 탐색 구조, 모바일 참가자 동선 개선이 필요하다.

## 3. 운영자 계정 3개

- 활성 운영 계정은 총 3개를 기본 운영 구성으로 삼는다. 역할은 총괄 1명과 운영자 2명이다.
- 기존 운영 계정 현황을 먼저 점검해 3개 안에 매핑한다. 기존 관리자 계정을 임의 삭제하거나 비밀번호를 덮어쓰지 않는다.
- 공유 로그인 대신 각자의 계정·이름·아바타를 사용한다. 누가 배정·답변·분류·정책 변경을 했는지 남긴다.
- 세 명 모두 공동 문의와 운영 현황을 볼 수 있고 답변·인수인계할 수 있다.
- 총괄은 계정·권한, 공통 답변 정책, 기본 매칭 기조를 관리한다. 운영자는 허용된 범위에서 회차별 기조 선택·비교·적용과 일상 업무를 수행한다.
- 정확한 이름·이메일은 계정 생성 직전에 정한다. 지금은 운영자 A/B/C로 설계한다. 영구적으로 ADMIN 행을 3개로 제한하는 DB 제약은 만들지 않는다.

## 4. 참가자 문의와 공동 문의함

### 참가자 경험

- 주요 화면에 일관된 문의 진입점을 둔다. 문의 목록·답변 내역은 별도 화면에서도 확인할 수 있다.
- 신청·결제·식탁 화면에서 문의하면 관련 신청/결제/식탁이 자동 연결된다. 참가자에게 같은 정보를 다시 입력하게 하지 않는다.
- 카테고리, 제목/내용, 관련 일정 등을 입력하고 접수 번호와 처리 상태를 확인한다.
- 운영자가 답변하면 웹 문의함과 인앱 알림에 반영된다. 추가 질문을 이어 쓸 수 있다.
- 비회원도 일반 문의를 접수할 수 있게 설계한다. 개인별 내역 열람·답변 확인은 로그인 또는 이메일 소유 확인 후 허용한다. 이메일 전달은 실제 발송 수단 연결·검증 후 제공한다.
- 해결 후 도움이 되었는지 간단히 묻고, 다시 질문하면 재접수 상태로 열린다.

### 운영자 경험

기본 화면은 왼쪽 문의 목록, 가운데 대화·처리 이력, 오른쪽 참가자·신청·결제·식탁 정보로 구성한다. 작은 화면에서는 목록과 상세를 분리한다.

- 공통 보기: 전체 / 미배정 / 내 담당 / 답변 대기 / 참가자 응답 대기 / 해결 완료.
- 기본 카테고리: 참가·일정, 결제·환불, 매칭·배정, 식당·현장, 채팅·이용 방법, 안전·신고, 기타.
- 대표 카테고리 1개와 복수 태그를 사용한다. 태그 예: 첫 참가, 일정 변경, 이용권, 재참가, 긴급 확인.
- 담당자, 우선순위, 처리 상태, 다음 확인 시각을 관리한다. 최초에는 직접 배정과 인수인계를 구현하고 자동 분배는 후속으로 둔다.
- 공개 답변과 운영자 내부 메모를 입력 영역·색상·서버 권한에서 구분한다. 사용자 API에는 내부 메모를 반환하지 않는다.
- 누가 언제 어떤 답변을 보냈는지, 담당·분류·상태를 어떻게 바꿨는지 타임라인에 남긴다.
- 다른 운영자의 열람·작성 상태를 표시하고, 오래된 버전으로 보낸 답변과 중복 전송을 감지한다. 브라우저 재연결로 같은 답변이 두 번 전송되지 않게 한다.
- 답변 템플릿은 실제 정책·결제 상태에 맞는 변수로 채운다. 미확정 환불을 완료된 것처럼 안내하지 않는다.
- 문의 처리에서 환불·일정 조정 등이 필요하면 관련 업무 화면으로 연결한다. 문의를 해결했다고 결제 상태가 저절로 바뀌지 않게 한다.
- 관련 문의를 제품 개선 과제와 연결한다. 자주 발생하는 문제는 FAQ·운영 정책·매칭 개선 후보로 모은다.

### 차별화 방향

채널톡의 공동 상담 방식을 참고하되, 참가자의 신청→결제→배정→참석→후기 맥락을 한곳에 연결한다. 같은 식탁의 문의가 반복되는지, 정책 변경 후 같은 문제가 줄었는지까지 추적하는 서비스 전용 운영 도구로 발전시킨다.

초기에는 사람이 분류·답변하고 템플릿을 사용한다. 이후 분류 추천·대화 요약·답변 초안을 추가하되 근거와 불확실성을 표시하고 운영자가 전송한다. 외부 AI에 개인 대화나 연락처를 무조건 전달하는 구조로 시작하지 않는다.

## 5. 매칭 기조 선택과 결과 비교

### 운영자에게 제공할 기조

| 기조 | 강조하는 요소 | 사용자에게 설명할 방향 |
| --- | --- | --- |
| 균형형 | 기존 운영 기준을 바탕으로 전반적 균형 | 취향과 구성의 균형을 고려한 식탁 |
| 공감·취향형 | 공통 관심사와 편안한 대화 성향 | 공통 주제로 자연스럽게 대화하기 좋은 식탁 |
| 새로운 발견형 | 처음 만나는 사람, 새로운 관점 | 새로운 사람과 취향을 발견하는 식탁 |
| 편안한 대화형 | 대화 속도·경청·분위기 선호 | 자신의 대화 방식에 맞춰 편하게 참여할 식탁 |

마지막 기조에 필요한 새 정보는 참가자가 명시적으로 선택하거나 후기로 확인한 선호를 사용한다. MBTI만으로 대화 성향을 단정하지 않는다. MBTI 점수는 검증이 필요한 휴리스틱으로 취급한다.

### 실행 원칙

- 기본 기조와 회차별 기조를 둔다. 실제 적용된 기조·가중치·버전은 매칭 실행에 고정 저장한다.
- 결제·동의, 4~6명, 동의된 공통 일정·지역, 최대 연령 폭 8년, 차단·신고·명시적 상호 제외는 기조와 무관하게 지킨다.
- 같은 참가자 스냅샷·정책 버전·시드이면 결과를 재현한다. 새로고침마다 무작위로 섞지 않는다.
- 기조를 바꾸면 후보 조합의 우선순위가 조금 달라지도록 한다. 후보가 부족하면 조합이 그대로일 수 있으며 그 이유를 표시한다.
- 미리보기에서 기존안/변경안의 확정 인원, 미매칭 인원, 구성 변화, 관심사 공통점, 예상 점수 등을 비교한다. 예상 점수를 실제 만족도로 표현하지 않는다.
- 미리보기는 알림·예약·채팅방 생성·결제를 수행하지 않는다.
- 적용은 참가자 데이터 변경 여부를 재확인하고 수행한다. 이미 확정·안내된 식탁을 정책 선택만으로 조용히 뒤섞지 않는다.
- 정상 회차는 마감 시 선택된 기조로 자동 실행한다. 매번 운영자가 검수해야 하는 흐름으로 바꾸지 않는다.
- 현재 18명 초과 구간의 첫 후보 우선 선택 방식은 재검토한다. 충분한 후보 조합을 점수로 비교하는 제한된 탐색을 적용하고 실행 시간과 결정성을 검증한다.
- 상세 가중치는 고급 설정으로 남기고, 주 동작은 기조 선택·비교·적용으로 단순화한다.

## 6. 후기와 다음 매칭 개선

### 후기 수집

- 행사 종료 후 알림·지난 식탁·홈의 다음 할 일에서 후기 진입을 제공한다. 작성 예상 시간은 1~2분을 목표로 한다.
- 식탁 전체, 대화, 식당 만족도와 재참여 의향을 받는다.
- 좋았던 점/아쉬웠던 점을 분리하고 구조화된 태그와 선택형 설명을 함께 받는다.
- 예시 태그: 공통 관심사, 대화 분위기, 다양한 관점, 시간·장소, 인원 구성, 소음·음식.
- 다음에는 어떤 분위기·관심사·일정을 선호하는지 참가자가 확인해서 저장한다.
- 상대에 대한 좋아요·피하고 싶은 상대는 비공개다. 안전 신고는 별도 처리 경로로 연결한다.
- 실제 참석과 연결해 후기 적격성을 검사하고, 노쇼·가상 참석 데이터를 실제 개인화 학습에 섞지 않는다.

### 개선 루프

1. 참가 조건·명시 선호와 매칭 정책 버전, 실제 구성, 참석, 후기를 연결해 기록한다.
2. 식당·안내 문제와 사람 구성 문제를 분리한다. 식당 점수가 낮았다고 구성원 사이의 궁합을 일괄 낮추지 않는다.
3. 명시적 다음 선호와 재회 제외는 규칙으로 반영한다. 긍정 피드백은 공통 주제·분위기 선호의 보조 근거로 누적한다.
4. 신규 참가자는 기본 정책을 사용하고, 반복 참가자도 소수 후기만으로 성향을 확정하지 않는다. 신호의 근거·표본 수·시점을 관리한다.
5. 개인화 점수의 영향은 제한하고, 운영자가 회차별로 켜고 끄거나 이전 정책으로 되돌릴 수 있게 한다.
6. 운영 화면에 규칙 버전별 실제 후기·재참여 결과를 제시한다. 시간 순서를 지킨 검증 데이터와 비교 가능한 회차를 사용해 개선 여부를 확인한다.
7. 충분한 데이터가 모이면 기조별 제한된 실험을 한다. 응답률·표본 수·불확실성을 함께 보여주고, 단순 평균 상승만으로 원인을 단정하지 않는다.

원문 문의를 곧바로 개인 궁합 점수로 바꾸지 않는다. 문의는 반복 문제 발견에 사용하고, 개인 선호 변경은 참가자에게 확인받는다. 운영자에게는 필요한 범위의 자료를 제공하고 다른 참가자에게 민감한 평가나 추론을 공개하지 않는다.

데이터 해자의 핵심은 후기 개수 자체보다, 어떤 정책으로 누구를 연결했고 실제로 어떤 경험과 재참여가 발생했는지 연결된 기록 및 개선 실험을 지속하는 능력이다.

## 7. 디자인 개편

### 방향

현재의 크림 배경·브라운 텍스트·세이지 강조와 편안한 다이닝 분위기를 유지한다. 타이포 위계, 여백, 정보 밀도, 상태 표현과 화면별 핵심 행동을 다시 설계한다. 모든 정보를 동일한 카드로 반복하지 않는다.

- 참가자: 모바일 우선. 홈의 중심은 다음 행동, 다가오는 식탁, 나와 어울리는 이유다. 하단 탐색은 홈 / 내 식탁 / 문의 / 마이로 단순화한다.
- 공개 홈: 서비스 방식, 예시 큐레이션, 검증된 후기, 참가 조건 등록, 문의를 자연스럽게 연결한다. 모의 후기를 실제 고객 추천으로 표시하지 않는다.
- 문의: 작은 대화 패널과 전체 내역 화면을 함께 제공한다. 미답변·새 답변·해결 상태가 눈에 들어오게 한다.
- 운영자: 고정 사이드바, 업무 배지, 검색과 필터, 넓은 대화 영역, 우측 맥락 패널. 문의/오늘 운영/매칭/후기 분석/설정으로 구성한다.
- 매칭: 숫자 입력 폼을 기조 카드·비교 화면·실행 기록으로 바꾼다.
- 후기: 점수 나열보다 좋았던 경험과 다음 희망을 쉽게 표현하는 짧은 단계형 화면으로 만든다.
- 공통: 색상·타입·간격·버튼·입력·상태·모달·빈 상태를 토큰과 컴포넌트로 정리한다. 키보드 탐색, 포커스, 대비, 작은 화면, 로딩·오류·중복 클릭 상태를 검증한다.

## 8. 데이터·기술 구성

현재 Next.js·PostgreSQL·독립 워커를 확장한다. 개발 SQLite도 동일한 업무 동작을 유지한다.

| 영역 | 추가/확장할 기록 |
| --- | --- |
| 운영자 | 운영자 프로필·권한·활성 상태 |
| 문의 | 문의, 공개 메시지, 내부 메모, 담당자, 카테고리·태그, 참여·읽음 상태, 변경 이력 |
| 매칭 | 기조·버전, 회차별 적용, 후보 스냅샷·비교 결과, 적용 이력 |
| 후기 | 긍정/불편 태그, 확인된 다음 선호, 집계 신호·출처, 실제/모의 구분 |
| 개선 | 문의 연결 개선 과제, 정책별 성과, 실험·롤백 기록 |

문의 실시간 갱신은 3인 협업 규모에 맞춰 폴링으로 시작하되 서버 버전 검사로 충돌을 처리한다. 후속으로 SSE 등 전송 방식을 교체할 수 있게 한다. 예약 알림·답변 알림·후기 집계 등은 기존 워커와 중복 방지 구조를 재사용한다.

텍스트 문의·답변부터 완성하고 파일 첨부·외부 메신저 통합·자동 AI 응답은 후속으로 둔다. 결제·환불은 모의 처리를 유지한다. 2026-10-18 사용자 결정에 따라 실제 결제·환불 연동과 이메일 발송은 도입하지 않으며 후속 작업에도 포함하지 않는다.

## 9. 구현 순서와 완료 기준

| 순서 | 작업 | 완료를 판단할 시나리오 |
| --- | --- | --- |
| 1 | 화면 구조·디자인 토큰·권한·데이터 구분·이벤트 설계 | 참가자/운영자 핵심 화면과 상태 설계, 기존 데이터 보존 및 마이그레이션 검증 |
| 2 | 운영자 3인과 공동 문의함 | A가 배정, B가 내부 메모, C가 공개 답변·분류 후 해결. 사용자는 답변과 상태만 확인. 동시 답변 충돌과 본인 외 문의 접근 차단 검증 |
| 3 | 매칭 기조·비교·회차 적용 | 동일 참가자 묶음을 여러 기조로 비교하고 적합한 안을 선택. 필수 조건 위반 0건, 미리보기 부수 효과 0건, 마감 자동 실행과 재현성 확인 |
| 4 | 후기 개편·명시 선호·개선 분석 | 실제 참석 후 후기→선호 확인→다음 매칭 반영을 추적. 식당 불편과 개인 선호 신호 분리, 가상 데이터 제외, 이전 정책 복구 확인 |
| 5 | 디자인 완성·통합 검증·배포 | 모바일 문의/신청/후기와 데스크톱 3인 협업을 실제 브라우저로 검증. PostgreSQL·워커·롤백 경로 확인 후 운영 반영 |

각 단계는 데이터베이스와 실제 화면이 연결된 상태로 완료한다. 고정 응답이나 빈 화면을 채우기 위한 숫자로 기능 완료를 대신하지 않는다. 단계마다 모의 운영 시나리오와 스크린샷·검증 결과를 남긴다.

## 10. 통합 시연 시나리오

1. 참가자가 일정·취향을 입력하고 모의 결제한다.
2. 매칭 관련 문의를 남긴다. 운영자 A가 맡고 B가 내부 메모로 돕고 C가 확인된 안내를 남긴다. 카테고리와 처리 이력이 보인다.
3. 운영자가 회차의 기조를 선택하고 비교 결과를 확인한다. 마감 시 시스템이 자동으로 확정·식당·채팅·안내를 준비한다.
4. 참가자는 배정된 식탁과 어울리는 이유를 확인하고 참석한다.
5. 종료 후 좋았던 점·아쉬웠던 점·다음 희망을 남긴다.
6. 다음 신청에서 확인된 선호와 누적 경험이 반영되고, 운영자는 정책별 후기·재참여와 반복 문의 변화를 확인한다.

이 시나리오가 끝까지 이어지는 것이 이번 확장의 최종 완료 기준이다.
