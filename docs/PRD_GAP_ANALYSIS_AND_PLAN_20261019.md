## 1. 결론과 검토 범위

회원가입·프로필, 복수 일정 신청, 모의 결제·환불, 자동 확정, 채팅, 체크인, 비공개 후기·신고, 운영자 협업까지 핵심 기능의 기반은 구현되어 있다. 그러나 **PRD의 모든 완료 조건을 충족했다고 판단할 수는 없다.** 특히 모집 회차와 신청 경로의 불일치, 여러 회차를 함께 고려하지 못하는 매칭, 날짜별 식당 재고 부재, 자동 안내 누락, KPI 정의 차이를 먼저 해결해야 한다.

이번 검토는 원본 PRD → 화면·API → 서비스·워커 → DB 마이그레이션 → 테스트를 대조했다. 기존 `PRD_TRACEABILITY_20261018.md`의 구현 선언을 그대로 완료 판정으로 사용하지 않았다. 코드에서 확인한 사항, 실행으로 재현한 사항, 추가 검증이 필요한 사항을 구분한다. 아래 목록은 이 범위에서 발견한 차이의 전체 목록이며, 운영 환경·모든 브라우저 상태에 대한 무결함 보증은 아니다.

## 4. 상세 차이와 분석

이하 `즉시/높음/보통/후속`은 이번 구현 순서이며 원문 P0/P1/P2와 별개다.

### G01. 모집 회차와 참가 신청이 서로 다른 체계 — 즉시, 코드 확인

- PRD: APP-01, STA-02, MAT-01, §11, INF-07.
- 근거: `app/api/availability/route.ts:11`, `lib/availability.ts:20`, `components/application-form.tsx`, `app/api/admin/events/route.ts`.
- `/apply`는 운영 회차 목록 대신 내일부터 60일의 달력을 받는다. POST는 날짜×지역마다 `availability_slots`가 없으면 **19:30 시작, 21:30 종료, 시작 2시간 전 마감, 정원 120, 가격 8,000원** 회차를 생성한다.
- 운영자가 등록한 같은 날짜·지역 회차라도 슬롯 연결이 없으면 별도 회차가 생길 수 있다. 신청 UI에는 실제 회차별 마감 시각이 없다. 운영 API는 생성/조회 중심이고 종료 시각·별도 자동 실행 시각·수정·모집 중단 흐름이 충분하지 않다.
- 행사 2시간 전에 처음 확정되는 회차는 정상적으로 하루 전 상세 장소 리마인드를 보낼 수 없다. 단순 알림 버그보다 일정 정책의 충돌이다.
- 계획: 운영 회차를 단일 원천으로 사용. 희망일 수요 수집을 유지한다면 모집 신청과 분리하고 결제 전에 실제 회차에 연결. 기존 중복 회차는 신청·방·원장 보존 후 명시적 매핑. 시간/정원/마감/종료/모집 상태 수정과 영향 미리보기 제공. 늦은 확정은 즉시 안내로 분기.
- 완료 기준: 미모집 날짜는 결제 불가, 같은 운영 회차에 신청 연결, 마감 표시, 운영 수정 시 기존 신청 보호, D-1·당일 확정 경계 검증.

### G02. 여러 회차를 함께 최적화하지 않아 가능한 참가자를 놓침 — 즉시, 실행 재현

- PRD: STA-03, MAT-08~09, §7.1의 전체 조합 최적화.
- 근거: `lib/matching-policy.ts:51`의 `matchingPlan`은 회차를 마감·ID순으로 순회하고 앞 회차에서 쓴 신청자를 뒤 회차에서 제외한다. 뒤 회차의 미매칭을 보고 앞 회차 배치를 되돌리지 않는다.
- 직접 재현: A/B는 다른 날, 각 정원 6. 신청자 0~3은 A만, 4~7은 A/B 선택. 전원 동년생·공통 관심사·동일 MBTI, 성별 교대, 최소 점수 0, 기존 좌석 없음, A 마감이 먼저.
- 실제: A=`[0,1,2,4,5,7]`, B=없음, 미매칭=`[3,6]`, 총 6명. 가능한 해: A=`[0,1,2,3]`, B=`[4,5,6,7]`, 총 8명. 기존 테스트 65개가 통과해도 이 반례는 남는다.
- 계획: 연결된 회차 후보군 전체의 배치 수를 먼저 최대화하고 다음으로 점수·재배치 우선순위를 평가. 제한 탐색·교환 탐색으로 구현하되 기존 확정 식탁은 고정. 탐색 예산과 중단 이유 기록.
- 완료 기준: 위 반례 8명 배치, 입력 순서·ID 변경에 의한 불필요한 미배정 제거, 동일 스냅샷 결정성, 19/25/50/100명 실행 시간 측정, 모든 필수 조건 보존.

### G03. PRD 재배치 우선순위와 최초 재배치 이력 부족 — 높음, 코드 확인

- PRD: §7.2, §7.4, MAT-12.
- 현재: 일반 매칭은 마감·ID순. `repairTable`은 원회차 우선 후 ID순. 같은 날짜/지역 → 같은 날짜/다른 지역 → 다른 날짜/같은 지역 → 다른 날짜/다른 지역의 비용을 명시적으로 비교하지 않는다.
- `lib/operator-workspace.ts`의 `reallocationCount`는 주로 `REPAIRED` 설명에서 계산한다. 최초 조합 탈락·대체 후보 탐색은 같은 수준의 구조화 이력으로 남지 않는다.
- 계획: 최초 희망 기준과 재배치 단계·출발/도착·실패 사유·최종 확정 시각을 별도 이벤트로 기록. G02 목적함수에 PRD 순서를 적용하고 참가자에게 상세 점수 없는 설명 제공.
- 완료 기준: 4단계 우선순위별 경계 테스트, 최초 재배치와 취소 복구를 구분한 이력·CSV·지표 일치.

- 계획: G01~12 적용 후 격리 SQLite/PG 동일 시나리오, 프로덕션 번들 E2E, 실기기 푸시와 마이그레이션 리허설. 최신 문서·운영 버전·테스트 증거를 분리해서 갱신.
- 완료 기준: PRD §18 12단계 연속 성공 + 실패 경로, 데이터 보존 대조, 웹/워커 같은 버전, 초기 신청 5분 목표 실제 측정. 이 문서 작성만으로 배포를 실행하지 않는다.

### 필요한 데이터 변경 후보

실제 이름·번호는 구현 시 최신 마이그레이션을 확인해 결정한다. 현재 027 다음 번호부터 PostgreSQL/SQLite 쌍으로 추가하며 기존 파일을 덮어쓰지 않는다.

1. 회차: 모집 상태, 명시적 종료/매칭 시각, 운영 회차-희망일 매핑, 수정 버전.
2. 재배치: 실행별 출발/도착·단계·이유·전환 시각·자동/수동 출처. 복구 세션과 초대 상태 연결.
3. 식당: 날짜/시간별 재고, 휴무, 임시 점유와 만료, 식이 확인 범위·기한·담당자.
4. 안내: 업무 이벤트 아웃박스, 템플릿 버전, 변수 스냅샷, 사용자/채널 전달 결과.
5. 개인정보: 요청 상태·보류 사유·처리 범위·실행 결과. 실제 보관 기간은 제품 정책 확정 후 적용.

기존 데이터에 근거 없는 자동/수동 출처·재배치 횟수·방문 시점을 소급 생성하지 않는다. 불명확한 과거 값은 UNKNOWN으로 유지한다.

## 6. 최종 인수 시나리오

1. 운영자가 회차와 식당 슬롯을 열고 참가자들이 프로필·동의·일정을 입력한다. 미모집/마감 날짜는 신청할 수 없다.
2. 승인/실패/취소/기존권 흐름이 원장·신청·화면에서 일치하고 새로고침 후 복구된다.
3. 마감 후 자동 실행한다. 4~6인·나이 차·제외 관계·정원을 지키며 다중 회차 반례를 전원 배치한다.
4. 정상 조합은 승인 없이 확정된다. 부족 조합은 PRD 우선순위로 재배치하고 실패 이유를 기록한다.
5. 식당 재고·식이 확인을 통과한 식탁에 방·예약 정보·안내를 한 번만 생성한다.
6. 미매칭 사용자는 실행 가능한 대안 또는 보관·환불을 선택한다. 기존 결제는 중복 승인되지 않는다.
7. 취소로 3명이 된 식탁에 응답 기한 초대를 보내고, 소진 후 3+3 병합 등을 시도한다. 작업 경합에도 중복 좌석이 없다.
8. D-1/늦은 확정 리마인드와 시작 콘텐츠를 검증한다. 푸시 실패·만료 구독·워커 재시작을 포함한다.
9. 참석자만 후기 요청을 받고 미응답 후속은 한 번이다. 노쇼 후보 검토·신고 조치·참석 정정이 연결된다.
10. 비공개 선호는 다음 매칭에 반영되고 다른 참가자에게 노출되지 않는다.
11. 운영 지표는 정의된 집단과 수기 정답값에 일치하며 모의 데이터·실제 데이터가 분리된다.
12. 삭제 요청 처리·이력·권한·데이터 보존, 모바일 처음 신청 시간까지 확인한 후 추적표를 갱신한다.
