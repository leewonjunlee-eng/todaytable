# 참가권 결제·환불 구현 기록

실제 금액 이동과 PG·이메일 호출은 연결하지 않는다. 첫 진입 안내에서 이 조건을 설명하며, 이후 화면에서는 실제 서비스와 같은 결제·환불 상태와 영수증을 보여준다.

- `/apply`: 일정·지역 → 참가권·규정 → 결제 승인. 승인 실패와 사용자 취소는 결제 시도에 남고, 신청·이용권 차감·승인 원장은 생성되지 않는다. 새 요청 키로 재시도할 수 있다.
- 승인 성공: 결제, 승인 원장, 신청, 이용권 생성·1회 사용, 마감 작업 등록을 하나의 트랜잭션으로 저장한다. 같은 요청의 재전송은 기존 결과를 반환한다.
- `/applications/[id]`: 신청·결제·매칭을 분리해 표시하고 마감과 다음 행동을 안내한다. 미매칭 시 일정 이동·참가권 보관·환불 중 직접 선택한다.
- 일정 이동은 결제를 유지한다. 참가권 보관은 사용한 1회를 한 번만 복원한다. 전액 환불은 기존 환불 작업을 통해 처리하고 원장에 반환 금액을 한 번 기록한다.
- `/payments`: 결제 성공·실패·취소, 영수증 번호, 원결제와 누적 환불 금액, 승인·환불 거래, 남은 참가권을 확인한다. 종료된 3회권의 잔여 횟수는 회당 5,000원으로 환불한다. 진행 중인 신청이 있으면 먼저 취소·보관하도록 제한한다.
- 환불은 소유자·승인 금액·남은 금액을 확인하고 초과 또는 중복 반환을 차단한다. 원래 결제 금액은 수정하지 않는다. 기존 원장 도입 전 데이터는 기존 승인 기록을 `LEGACY` 출처로 기록한다.
- 홈과 내 식탁에서 미매칭 해결 요청 및 대기자 자리를 보여준다. 새 날짜·지역의 대기자 제안은 참가자의 명시적 수락 후에만 확정한다.

검증: `tests/virtual-payments.test.ts` 7개 시나리오를 SQLite와 PostgreSQL에서 각각 통과했다. 360/390/430px 브라우저에서 승인 실패·취소·재시도·영수증·부분 환불을 확인했고, 별도로 미매칭 전액 환불 UI → 실제 worker → 완료 영수증을 확인했다. 가로 넘침과 페이지 JavaScript 오류는 없었다. 브라우저 데이터는 별도 격리 DB만 사용했다.
