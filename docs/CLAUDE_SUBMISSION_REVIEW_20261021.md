## 향후 개선 (3건)
1. **화면이 숨겨지면 새로고침 멈추기:** `useJourney`에서 `document.hidden`일 때 주기적 요청을 멈춥니다. 40곳 가까이 쓰이고 있어 모바일 배터리, 데이터, 서버 부하에 도움이 됩니다.
2. **채팅 사용성:** 채팅방을 열거나 새 메시지가 오면 최신 메시지로 스크롤합니다. 전송 버튼에 `onPointerDown` preventDefault를 걸어 보낸 뒤에도 키보드가 닫히지 않게 합니다. 실기기 확인이 필요합니다.
3. **로그인·결제 화면 문구:** 로그인 화면 제목 "다시 만나 반가워요"는 처음 온 사람에게 어색합니다. 처음 온 사람을 위한 가입 안내를 더 눈에 띄게 보여 주면 좋습니다. 결제 단계의 "결제 처리 결과 선택"(`application-form.tsx:24`)은 "체험용 결제 결과 선택"처럼 체험용이라는 점을 분명히 하면 좋습니다.

## 잔여 위험 (구체적인 것만)

**R1. 프로필이 없는 참가자가 로그인하면 `next`가 사라짐 (MEDIUM-LOW, 제출 전 권장)**
- **코드로 확인한 사실:** `app/api/auth/login/route.ts:28`에서 프로필이 없으면 무조건 `'/profile/test'`를 반환합니다.
- **영향:** 가입 후 프로필 작성을 중간에 그만둔 사람은 흔합니다. 이 사람이 나중에 날짜 카드나 식탁 링크로 다시 로그인하면 결국 `/apply`로 가게 되어, 이번 2번 수정이 이 경로에서는 적용되지 않습니다.
- **최소 수정:**
  ```ts
  const dest=loginDestination(body.next,operatorLogin);
  …next: profile ? (dest ?? (operatorLogin?'/admin':'/')) : (dest?`/profile/test?next=${encodeURIComponent(dest)}`:'/profile/test')
  ```
  프로필이 없는 계정은 참가자뿐이고 운영자 로그인은 403에서 걸러지므로, 참가자 허용 목록만 적용됩니다.

**R2. 응답이 유실된 뒤 문구를 고치면 채팅 전송이 계속 409로 실패함 (LOW-MEDIUM, 원래 있던 문제)**
- **코드로 확인한 사실:** 실패하면 요청 키를 그대로 유지합니다(`journey-pages.tsx:48`). 서버는 같은 키로 다른 내용이 오면 409를 반환합니다(`messages/route.ts:42,49`).
- **영향:** 서버에는 저장됐는데 모바일 망에서 응답만 유실되면, 사용자가 문구를 고쳐 다시 보낼 때마다 계속 409가 납니다. 새로고침하기 전까지 대화방을 쓸 수 없습니다. Codex의 테스트는 같은 문구로 재시도하는 경우만 확인합니다.
- **최소 수정:** 요청 키를 문구에 묶습니다. `const keyBody=useRef('')`를 두고, `send`에서 `if(keyBody.current!==submittedBody.trim()){key.reset();keyBody.current=submittedBody.trim();}`를 실행한 뒤 `key.next()`를 부릅니다. 테스트에는 "실패 → 문구 수정 → 새 키" 경우를 추가하면 됩니다.

**R3. 보낸 직후 메시지가 최대 4초간 보이지 않을 수 있음 (LOW-MEDIUM, 추정, 원래 있던 문제)**
- **코드로 확인한 사실:** `useJourney`는 진행 중인 요청이 있으면 그 요청을 그대로 돌려줍니다(`journey-ui.tsx:46,69`).
- **추정 (Codex가 GET 지연 intercept로 확인 필요):** POST가 저장되기 전에 시작된 폴링이 진행 중이면, 전송 후 `q.refresh()`가 그 오래된 결과를 받습니다. 입력란은 비워졌는데 메시지는 다음 폴링 때까지 보이지 않습니다. 사용자가 실패한 줄 알고 다시 보낼 수 있습니다. 같은 방식으로 refresh하는 출석 정정과 예외 처리 화면도 영향을 받습니다.
- **최소 수정:** `const refresh=useCallback(()=>inFlight.current?inFlight.current.then(()=>load()):load(),[load])`. 진행 중이던 요청이 끝나면 `inFlight`를 비우는 핸들러가 먼저 실행되므로, 이어지는 `load()`는 새 요청을 보냅니다.

**R4. 노치가 있는 iPhone에서 포커스된 제목이 상단바에 가려질 수 있음 (LOW, 추정)**
- **코드로 확인한 사실:** 스크롤 여백은 `html{scroll-padding-top:75px}`입니다(`app/mobile.css:4`). 그런데 참가자 상단바 높이는 `calc(64px + env(safe-area-inset-top))`입니다(`participant-mobile.css:23`). `viewportFit:'cover'`라서 노치 기기에서는 상단바가 75px보다 높습니다.
- **최소 수정:** `scroll-padding-top:calc(75px + env(safe-area-inset-top))`.

**R5. 결제 대기 신청을 불러오면 페이지가 열리자마자 포커스와 스크롤이 이동함 (LOW)**
- **코드로 확인한 사실:** `application-form.tsx:15`의 결제 대기 복원이 `setStep(2)`를 실행하면, `:11`의 효과가 동작해 페이지를 연 직후 h1과 뒤로 가기를 건너뛰고 제목으로 이동합니다.
- **최소 수정:** 복원할 때 `previousStep.current=2;`를 `setStep(2)` 직전에 넣습니다.

**참고 (사소함):**
- 최종 단계 경고는 "이전 단계에서 선택"하라고 하지만, 실제로는 7번 뒤로 가야 합니다. 경고 옆에 `setStep(0)` 버튼("성별 선택으로 이동")을 두면 좋습니다(`profile-test.tsx:37`).

## 공유 훅 경쟁 상태 검토: 비차단, 선택 수정

**R3 수정으로 기존 문제의 발생 구간이 조금 넓어졌습니다 (LOW).**
- **무엇이 문제인가:** `mounted`는 effect가 다시 실행돼도 계속 같은 ref를 씁니다. 그래서 `refresh`가 기다리는 동안 같은 컴포넌트의 `path`가 바뀌면, 다시 마운트된 상태라 `mounted.current`가 true입니다. 이때 이전 주소용 `load`가 signal 없이 실행돼 이전 식탁의 데이터를 새 화면에 덮어쓸 수 있습니다(`journey-ui.tsx:51,71`).
- **어디서 생길 수 있나 (추정):** 채팅에서 메시지를 보낸 직후 1초 안에 `/tables/a/chat`에서 `/tables/b/chat`으로 이동하는 경우뿐입니다. 이 경우 같은 `ChatView`가 다시 쓰일 수 있습니다. 문의 대화(`TicketConversation`)는 `key`로 아예 새로 마운트되므로 해당하지 않습니다.
- **좁은 수정:** `const activePath=useRef(path);`를 두고 effect 안에서 `activePath.current=path`로 갱신합니다. 그리고 `:51`, `:53`, `:57`의 조건에 `&& activePath.current===path`를 더합니다. 제출을 막을 문제는 아닙니다.
